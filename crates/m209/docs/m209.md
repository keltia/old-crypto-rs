# Hagelin M-209 — implementation specification and source ledger

**Project:** `old-crypto-rs` / proposed independent `crates/m209` crate
**Status:** Step 4 — historical key fixtures transcribed; mechanical implementation pending
**Machine:** U.S. Army Converter M-209 / M-209-A / M-209-B; related U.S. Navy CSP-1500
**Baseline historical specification:** War Department, *TM 11-380*, 17 March 1944.

> This document distinguishes (H) statements directly checked against the historical manual, (R) observations from independently published reference software, and (D) proposed Rust design decisions. A cited demonstration is not evidence of unrestricted cross-version interoperability.

## 1. Scope and provenance

Implement the World War II U.S. M-209 **pin-and-lug** converter, not a generic postwar Hagelin family machine. The M-209 descends from Boris Hagelin's C-38 design; the historical U.S. device should not be described as a Crypto AG-manufactured M-209. Variants M-209, -A and -B are covered together by TM 11-380 (1944). (H)

## 2. Machine constants and electrical/mechanical behavior

### 2.1 Six rotating pin wheels (H)

Wheel numbers refer to physical order left-to-right, 1 to 6. The visible alphabets are:

| Wheel | Size | Visible letters |
|---|---:|---|
| 1 | 26 | `ABCDEFGHIJKLMNOPQRSTUVWXYZ` |
| 2 | 25 | `ABCDEFGHIJKLMNOPQRSTUVXYZ` (omits W) |
| 3 | 23 | `ABCDEFGHIJKLMNOPQRSTUVX` (omits W within A–X) |
| 4 | 21 | `ABCDEFGHIJKLMNOPQRSTU` |
| 5 | 19 | `ABCDEFGHIJKLMNOPQRS` |
| 6 | 17 | `ABCDEFGHIJKLMNOPQ` |

Source: H1, paragraph 5a. Each wheel has an effective/ineffective pin setting per visible letter. The *pin selection pattern is key material*, not fixed machine wiring. (H)

The pin physically sensing the drum can differ from the wheel letter at the reading index. A commonly published reference offset states that when the visible alignment is `AAAAAA`, the effective pins under consideration correspond to `PONMLK` (left to right). This indexing relationship is corroborated by the mechanical explanations in R1 and widely reproduced descriptions, but it must be verified against a full rotation trace before encoding it as a constant. **A visible wheel position is not automatically a pin-array index.**

### 2.2 Drum and lugs (H)

There are **27 drum bars**, with **two movable lugs per bar**. Lug positions are 1–6 for the numbered wheels or a neutral position `0`. The original hardware constrains the two physical lug columns; the data model must retain sufficient information to distinguish valid historical settings from a permissive simulator format. A bar displaces the print mechanism **at most once**, even if both of its lugs meet active pins. Thus the displacement is a count of *engaged bars*, not a count of individual engaged lugs; it ranges from 0 through 27.

The 1944 manual's example **Table II** (printed p. 15), transcribed in drum-bar order:

```text
 1  3-6       10  2-0       19  2-0
 2  0-6       11  2-0       20  2-5
 3  1-6       12  2-0       21  2-5
 4  1-5       13  2-0       22  0-5
 5  4-5       14  2-0       23  0-5
 6  0-4       15  2-0       24  0-5
 7  0-4       16  2-0       25  0-5
 8  0-4       17  2-0       26  0-5
 9  0-4       18  2-0       27  0-5
```

The manual explicitly calls these demonstration key lists **Tables I and II**. Do not silently substitute any modern default key list. The Table I pin settings were transcribed from the scanned original and added in `src/fixtures.rs` during Step 4.

### 2.3 Letter conversion (R, to reconcile against H1)

For zero-based plaintext contact `P` (`A = 0`, ..., `Z = 25`) and displacement `D`:

```text
output_index = (25 - P - D) mod 26
```

The same reciprocal transform is used in either direction **at the same wheel state**, followed by the historically correct stepping. This formula is a proposed computational normalization of the mechanical operation; confirm it against the manual's operational examples, particularly the direction/timing of advance, before freezing the implementation. The 27-bar count can exceed 25, so retain the full displacement before reduction modulo 26.

### 2.4 Stepping and indexing (H/R; verify mechanically in Step 5)

All six wheels advance as the handle is cycled, with their individual periods given above. Exact order of sensing, printing, and advancing must be fixed from the manual and independently tested; **do not infer it from a round-trip property alone**. An input character must see the same wheel state in both encryption and decryption.

## 3. Authentic historical verification fixture (H1)

**1944 manual: 26-letter setup check, printed pp. 13–18 (Tables I and II and paragraph 8).**

- Pin key: **exactly Table I**; to be transcribed and reviewed in Step 4.
- Lug key: **exactly Table II**, listed in §2.2.
- Initial visible wheels: `AAAAAA`.
- Input: `AAAAAAAAAAAAAAAAAAAAAAAAAA` (26 letters).
- Expected 26-letter check: `TNJUWAUQTKCZKNUTOTBCWARMIO`.

The expected check is legible in the scanned H1 Table II page and agrees with the widely reproduced value. **This is a conditional, not yet executable, KAT:** it must not be run until the exact Table I pins and the indexing/advance conventions are transcribed and verified. Do not change this historical expected value to accommodate an implementation bug.

## 4. Independent software interoperability fixture (R1)

Published in Brian Neal's `M209` API documentation; machine settings and generated ciphertext are explicitly shown together.

```text
Initial visible wheels: FFEGJP
Drum lugs: 1-0 2-0*2 0-3 0-5*3 0-6 2-4 3-6
Effective pins, wheel 1: FGIKOPRSUVWYZ
Effective pins, wheel 2: DFGKLMOTUY
Effective pins, wheel 3: ADEFGIORTUVX
Effective pins, wheel 4: ACFGHILMRSU
Effective pins, wheel 5: BCDEFJKLPS
Effective pins, wheel 6: EFGHIJLMNP
Plaintext: THE PIZZA HAS ARRIVED
Expected ciphertext, grouped: QBCHU WCCDI YFNCH LOZJY G
Expected decoded display: THE PI  A HAS ARRIVED
```

This fixture tests the published simulator's **space→Z input normalization** and **Z→space decoded presentation**, which is lossy when the original message contains a literal Z. For a cryptographic-core test compare ungrouped ciphertext `QBCHUWCCDIYFNCHLOZJYG`, and explicitly normalize the input according to the documented convention. The display-level result is a **separate text-layer test**, not a raw-contact round-trip assertion.

Further full-message examples with external/system/key-list indicators are published in R1's procedure tutorial. Those values depend on fixed setup and indicators; random-key examples are not stable KATs unless every variable is pinned.

## 5. Proposed Rust design (D)

- Separate crate `crates/m209`; `docs/m209.md` is stored with that crate.
- Use canonical `old_crypto_rs::Block` exclusively; never introduce a duplicate local trait.
- Strongly typed `WheelId`, `WheelPosition`, `PinPattern`, `Lug`, `DrumBar`, `M209Config`; checked public constructors.
- Keep `M209Core` (fixed state conversion) separate from `M209Machine` (mutable wheel state) and a reset-per-call public `M209` facade.
- Store pin arrays compactly as wheel-specific bitsets and drum bars as 27 fixed-size pairs; no heap allocation is intrinsically required for per-character operation.
- Distinguish raw A–Z contact processing from loss-prone Army text conventions, indicators, grouping and padding.
- Validate historical mechanical restrictions separately from permissive experimentation; don't reject legitimate documented keys merely because optional wartime key-generation recommendations were not followed.
- Follow existing crates: Clap `m209ctl`, YAML key config, Divan benchmarks, explicit `[[bin]]` and `default-run`, and integration with `old-crypto-tui`.

## 7. Open verification items — no unsupported certainty

1. Independently transcribe **all six pin columns** from H1 Table I; compare against the photographed source, not Wikipedia or another transcription.
2. Resolve exactly which pin on each wheel is sensed for a given visible indicator and at which instant the wheels advance; compare against both H1 and R1.
3. Check whether the planned lug type should model the original left/right hardware columns, or normalize them after validating historic restrictions.
4. Distinguish operator **key-generation recommendations** (such as pin-run constraints and overlap recommendations) from intrinsic mechanical requirements; source any limits before enforcing them.
5. Independently verify one longer operational-message fixture with all indicators fixed before making it a CI known-answer test.
6. Determine which aspects of M-209, M-209-A, M-209-B can be represented by the same cryptographic core versus variant-specific procedures or mechanics.
